# 从一次排版问题看 Echo Founder

## 起点

项目负责人带着自己的题目和素材，尝试完成一篇公众号文章。稿件经方向调整和人工修改后，被本人确认采用；随后继续检查排版、复制和下载。

这是一名项目负责人参与、Codex 协助操作的试用，不是独立客户测试。此页只介绍问题和处理过程，不公开原始私人稿件。

## 发现的问题

排版结果缺失了 16 个段末句号，2 处引用也没有正确转换成链接。旧检查显示通过，说明“生成了 HTML”不足以证明正文没有变化。

另一个问题来自表达要求：“不要编造案例”等写作要求被误显示成公开限制警告，影响了成品阅读。

## 怎样调整验收标准

- 分别核对正文、标点与引用，不以页面能打开作为内容保真的证据。
- 将采用记录绑定到确切版本；正文或排版变化后，重新确认。
- 检查实际复制的富文本和实际下载文件，而不只检查预览。
- 区分写作要求与真正的保密、授权限制，保留后者。

后续根据负责人的视觉反馈接入 md2wechat，并保留确认过的标题断行、间距和主题参数。

## 已有结果

已采用的本地版本完成 25 个文本块和 2 处链接的核对，并验证了预览、复制及下载的一致性。完整过程保留了原稿与旧版本。

负责人自行粘贴到公众号后台后曾报告变化，之后选择暂按现状使用。因此，平台编辑器的精确保真仍未被证明。

内部安装包另有本机可靠性记录：2026-11-02 持续运行 1803.1 秒，60 轮、481 次页面与接口探测，零失败，退出后端口关闭。这项验证不包含真实模型持续负载或另一台 Mac 的独立试用。

## 这个案例说明什么

这里可展示的是把用户反馈转成可检查条件、保存失败证据、核对实际交付结果的过程。项目负责人承担需求与采用判断，Codex 协助实现和验证。尚未通过客户复用、付款或时间对照证明商业价值。
